# Decisions

This log records ambiguous or underspecified requirements and the choice
made, per CLAUDE.md's "Development behavior" rule: pick the safest/simplest
production-quality default and record it here.

## Phase 0 — Foundation

### 1. Dependency/tooling versions
The spec says "current stable versions" without pinning. Chose (as of
2026-09, verified installable from PyPI at implementation time):
Flask 3.1.x, SQLAlchemy 2.0.x, Flask-SQLAlchemy 3.1.x, Flask-Migrate 4.1.x,
Alembic 1.19.x, Flask-WTF 1.3.x, psycopg 3.3.x (binary extra for portability),
gunicorn 23.x, pytest 8.4.x, ruff 0.6.x, black 24.10.x, mypy 1.20.x.
`pyproject.toml` pins compatible ranges (`>=X,<Y`) rather than exact versions
so routine patch/minor updates don't require editing the file, while a major
bump is a deliberate decision.

### 2. Primary key strategy
DATABASE_DESIGN.md says "Use UUIDs for externally exposed identifiers where
practical" without mandating it for every table. Decision: introduce a
shared `app/models/base.py` with a `Base` abstract model using a UUID
primary key (stored as CHAR(36), dialect-independent) and a `TimestampMixin`
for UTC-aware `created_at`/`updated_at`. This gives Phase 1+ domain models a
consistent starting point without committing to any table structure yet
(no domain tables are defined in Phase 0, per its exit criteria).

### 3. Database portability in models
To let the same model definitions run against SQLite (tests) and PostgreSQL
(dev/prod) without maintaining two schemas, `GUID` is a custom
`TypeDecorator` over `CHAR(36)` instead of PostgreSQL's native `UUID` type.
This trades a small amount of native-type efficiency for CLAUDE.md's rule
"Make automated tests deterministic and independent of external services"
(tests do not require a running Postgres).

### 4. Local development database default
`DevelopmentConfig` falls back to `sqlite:///instance/dev.db` when
`DATABASE_URL` is unset, rather than failing hard like `ProductionConfig`
does. Rationale: a friendly zero-config `flask run` experience for local
iteration, while Docker Compose and CI always set `DATABASE_URL` explicitly
to PostgreSQL. `ProductionConfig.init_app` still raises `RuntimeError` if
`SECRET_KEY` or `DATABASE_URL` are missing, so production cannot silently
run against SQLite or a blank secret.

### 5. Initial ("foundation") migration is empty
Phase 0 explicitly allows a "near-empty/foundation-only" migration. Since no
domain models exist yet (Phase 1+ scope), `flask db migrate` produces no
autogenerated diff; the committed migration
(`migrations/versions/1279f3ba16bf_foundation_baseline.py`) is a deliberate
no-op revision that establishes the Alembic version chain so later phases
can `down_revision` off of it.

### 6. CSRF protection wiring now, forms later
Flask-WTF's `CSRFProtect` is initialized as a global extension in Phase 0
(empty attack surface today — no HTML forms exist yet) so that Phase 1's
login form and all subsequent admin/contact forms are CSRF-protected by
default rather than needing to remember to add it later. `WTF_CSRF_ENABLED`
is disabled only in `TestingConfig` to keep test clients simple; it is not
disabled in development or production.

### 7. Health vs. readiness semantics
`/healthz` reports process liveness only (no dependency checks) so an
orchestrator never kills a healthy process merely because the database is
briefly unreachable. `/readyz` executes `SELECT 1` against the configured
database and returns 503 on failure; this is the endpoint that should gate
traffic routing / load balancer registration. Both are unauthenticated by
design (standard practice for infra probes) and reveal no internal detail
beyond an "ok/ready" vs "unavailable" status.

### 8. Structured logging format
Logs are emitted as single-line JSON to stdout (12-factor style) rather than
to a file, since the Docker/Compose/production deployment targets in
ARCHITECTURE.md all expect container log collection from stdout. Each
request gets a `request_id` (from the incoming `X-Request-ID` header if
present, otherwise a generated UUID4) attached to every log line emitted
during that request and echoed back in the response header, satisfying the
"structured application logs" + "request IDs" observability requirement.

### 9. Docker build strategy
Multi-stage Dockerfile (builder installs into `/install` with build tools;
runtime copies only the installed site-packages plus source) to keep the
production image small and avoid shipping compilers. Runs as a non-root
`app` user, exposes 8000, and uses a `HEALTHCHECK` against `/healthz` per
the Docker skill's requirements. `docker-compose.yml` runs `flask db
upgrade` before starting Gunicorn on `app` container start, which keeps
"apply migrations" part of the standard startup path rather than a manual
step operators can forget — acceptable for this project's scale (a single
app instance/small deployment), and documented here as a explicit choice
since a large multi-replica production deployment would instead run
migrations as a separate release step.

### 10. Verification limits of this environment
Docker and `docker compose` are not available in the sandbox this phase was
implemented in (no `dockerd`, no root to install it, no existing socket).
`docker build` / `docker compose up` could not be executed directly. As a
substitute, equivalent verification was performed by: extracting the
`postgresql-16` Ubuntu package with `dpkg-deb -x` (no root required) to run
a real, disposable PostgreSQL 16 server; running `flask db upgrade` against
it (succeeded); and running the app under Gunicorn against that same
PostgreSQL instance, confirming `/healthz` and `/readyz` both return 200.
The Dockerfile and docker-compose.yml were reviewed manually and
docker-compose.yml was validated as well-formed YAML. This gap is also
recorded in docs/IMPLEMENTATION_STATE.md so it is visible to whoever runs
this phase's exit criteria on a machine with Docker available.

## Phase 1 — Authentication

### 11. Password hashing: Argon2id via argon2-cffi
docs/SECURITY.md explicitly requires "strong password hashing (Argon2id
preferred; bcrypt acceptable)". Werkzeug's `generate_password_hash` (already
a transitive dependency via Flask) defaults to `scrypt`/`pbkdf2`, neither of
which is Argon2id, so a dedicated `argon2-cffi` dependency was added.
`app/services/auth_service.py` wraps `argon2.PasswordHasher` (Argon2id is
its default variant) behind `hash_password`/`verify_password` so no other
module imports argon2 directly. Rehashing-on-parameter-change
(`PasswordHasher.check_needs_rehash`) was intentionally deferred - there is
exactly one account in this phase and no admin UI yet to surface a
"password was upgraded" flow; noted here for a later phase.

### 12. Role modeling: a `role` column, not a `Role` table
docs/DATABASE_DESIGN.md's `User` table (the authoritative schema reference)
defines a plain `role` field; docs/MASTER_PROMPT.md's data-model list also
names a separate `Role` table without describing its columns. Since exactly
one role (`admin`) is seeded/used in this phase and CLAUDE.md's "Development
behavior" rule says to pick the simplest production-quality default when
requirements are ambiguous, `User.role` is a `String(32)` column constrained
by a `CHECK (role IN ('admin'))` constraint rather than a normalized `Role`
table. A `Role` table can be introduced later (with a migration) if
multi-role RBAC becomes a real requirement - nothing in the auth/authorization
code assumes a single hard-coded role beyond this check constraint and the
`UserRole` enum.

### 13. Session/identity library: Flask-Login
Not mandated by name in any doc, but docs/SECURITY.md requires "session
rotation after login", "logout invalidation", and "session protection"-style
guarantees. Flask-Login is the de facto standard for this in Flask apps,
integrates directly with the already-configured session cookie settings in
`app/config.py` (`SESSION_COOKIE_HTTPONLY/SECURE/SAMESITE`,
`PERMANENT_SESSION_LIFETIME`), and needs no new infrastructure. Configured
with `session_protection = "strong"` (logs a session out if its
remote-addr/user-agent fingerprint changes) and the login route calls
`session.clear()` before `login_user()` to discard any pre-login session
content on privilege escalation (mitigates session fixation, since Flask's
cookie-based sessions don't have a server-side session ID to literally
rotate).

### 14. Login rate limiting: Flask-Limiter with in-process memory storage
docs/SECURITY.md requires rate limiting "at minimum" on admin login.
docs/ARCHITECTURE.md says "Do not introduce Redis in V1 unless required."
`app/config.py` (written in Phase 0) already anticipated
`RATELIMIT_STORAGE_URI`/`RATELIMIT_DEFAULT` - these are literally
Flask-Limiter's own config keys, so Flask-Limiter was the evidently-intended
choice. Its default `memory://` storage backend keeps per-key counters in
the worker process; this is correct for "a lightweight approach appropriate
for a self-hosted single-instance app" (the task's own framing) since
Gunicorn here runs as a small, fixed number of workers on one host with no
requirement for cross-instance-consistent counters. `LOGIN_RATE_LIMIT`
(new config key, default `"5 per minute;20 per hour"`) is evaluated
per-request via a callable passed to `@limiter.limit(...)` so it can be
tuned via environment variable without a code change. If this app is ever
scaled to multiple app instances behind a load balancer, `RATELIMIT_STORAGE_URI`
can be pointed at Redis with no code change (Flask-Limiter supports this
natively) - documented here rather than built now, per "avoid premature
caching"/no Redis-in-V1.

### 15. Admin bootstrap: idempotent CLI command, not automatic-on-every-boot
CLAUDE.md requires "no public admin-registration route" and "do not
silently delete or overwrite user content". `flask bootstrap-admin` (new
CLI command, app/cli.py) reads `ADMIN_BOOTSTRAP_EMAIL` and either
`ADMIN_BOOTSTRAP_PASSWORD_HASH` (preferred - pre-hashed, generated via the
new `flask hash-password` command) or `ADMIN_BOOTSTRAP_PASSWORD` (dev-only
plaintext convenience, hashed at bootstrap time) to create exactly one
administrator account. It is deliberately idempotent and never overwrites
an existing account with the same email - re-running it (e.g. on every
container start, as `docker-compose.yml`'s `app` command now does after
`flask db upgrade`) is safe. It does nothing (exit 0, informational message)
if `ADMIN_BOOTSTRAP_EMAIL` or both password variants are unset, so it is
safe to leave wired into the startup command even after an operator has
started managing the admin account through a future admin UI.

### 16. Login failure responses are deliberately generic
`auth_service.authenticate()` returns the identical `None` result (and the
login route shows the identical "Invalid email or password." message) for
"no such user", "wrong password", and "inactive account", and performs a
dummy Argon2 verification even when the email doesn't exist, so response
timing doesn't cleanly distinguish "unknown email" from "wrong password".
This follows docs/SECURITY.md's authorization/enumeration-avoidance spirit
even though it isn't spelled out verbatim for login. The `next` query
parameter that `login_required` appends on redirect is not honored as a
post-login redirect target in this phase (login always redirects to
`admin.dashboard`) - this sidesteps building/validating an open-redirect
allowlist for a single fixed destination; revisit if the admin app grows
multiple entry points worth returning to.

### 17. TestingConfig needed an explicit SECRET_KEY
Discovered while adding auth tests: Flask's session/flash machinery raises
at request time if `SECRET_KEY` is empty, which it was by default in
`TestingConfig` (falls through to `BaseConfig`'s `os.environ.get("SECRET_KEY", "")`)
whenever the `SECRET_KEY` environment variable isn't set. Since Phase 1 is
the first phase that actually touches the session (login), this Phase-0 gap
only surfaced now. Fixed by giving `TestingConfig` a fixed, clearly-labeled
non-secret default (`"testing-secret-key-not-for-production"`), still
overridable via the `SECRET_KEY` env var for parity with the other configs.

## Phase 2 — Portfolio content

### 18. SkillCategory is a global taxonomy, not Profile-scoped
docs/DATABASE_DESIGN.md's `SkillCategory` table has no `profile_id` column
(unlike every other content table in that section), while `Skill` has
`category_id` only. Since exactly one administrator/portfolio exists in
this application (Phase 1's scope, unchanged so far), treating
`SkillCategory` as a shared, unscoped list matches the authoritative schema
exactly rather than adding an unrequested `profile_id` column. The admin
routes still perform the same server-side ownership-style lookup pattern
(`skill_service.get_skill_category(id)` returning `None` on a nonexistent
id, 404 rather than a leak) for consistency and future-proofing, even
though there is currently only one admin who could ever see the list.

### 19. Skill.proficiency is an integer 1-5 scale with a CHECK constraint
docs/DATABASE_DESIGN.md lists `Skill.proficiency` with no type. A bounded
integer scale (rather than free text or a percentage) is simplest to render
as a fixed set of admin-form choices (`SkillForm`'s `SelectField`) and to
later render as a progress bar/star rating on the public site (Phase 4),
and a DB-level `CHECK (proficiency BETWEEN 1 AND 5)` constraint (mirroring
`User.role`'s existing CHECK-constraint convention from Phase 1,
docs/DECISIONS.md #12) enforces the bound even against a future direct-DB
write, not just the WTForms validator.

### 20. ProjectTechnology is authored as one comma-separated form field
docs/DATABASE_DESIGN.md's `ProjectTechnology` has its own `id`/`project_id`/
`name`/`display_order`, implying it could get its own full CRUD screen like
every other child entity. Instead, `ProjectForm.technologies` is a single
text field ("React, Flask, PostgreSQL") that
`project_service.sync_technologies()` parses and replaces wholesale into
individually-ordered `ProjectTechnology` rows on every save. A technology
tag has no independent identity/relationships worth preserving across an
edit (unlike, say, a Skill, which carries its own proficiency/years), so a
nested nine-screen sub-CRUD would add real UI complexity for no behavioral
benefit; the normalized rows docs/DATABASE_DESIGN.md specifies still exist
in the database exactly as designed, just authored as a list rather than
one-row-at-a-time.

### 21. Reordering is "move up"/"move down" buttons, not drag-and-drop
CLAUDE.md requires "content should support ordering" and separately lists
accessibility requirements including "keyboard navigation" and "reduced
motion consideration." A drag-and-drop reorder widget (the more visually
modern choice, and consistent with HTMX being in the stack) is not
reliably keyboard-/screen-reader-operable without significant extra ARIA
work, and this phase's UI is explicitly allowed to be "plain/unstyled-ish."
Two POST buttons per row ("Move up"/"Move down", `app/services/
portfolio_content.py`'s `move()`) give every admin an accessible,
zero-JavaScript way to reorder content today. The service layer also
implements `reorder_scoped()` (apply an arbitrary explicit id order in one
call, with the same IDOR-safe id-set validation as everything else in
`portfolio_content.py`) and is covered by tests, specifically so a future
HTMX drag-and-drop admin UI can call it directly without any model or
service change - only a new route/JS is needed then.

### 22. Generic CRUD/reordering engine + one route factory, not ten near-duplicates
Ten Phase 2 entities (SocialLink, Experience, Education, SkillCategory,
Skill, Project, ProjectTechnology, Certification, Achievement, Resume) share
the same shape: rows scoped to a parent, carrying `display_order`/`visible`.
Rather than writing list/get/create/update/delete/reorder once per entity
(and six nearly-identical Flask route sets), `app/services/
portfolio_content.py` implements that logic once, generically, and
`app/admin/routes.py`'s `_register_profile_scoped_crud()` factory registers
list/new/edit/delete/move-up/move-down routes for the five simplest
Profile-scoped entities from just a model + form + column list. Project and
SkillCategory/Skill are hand-written instead of forced through the factory
because they need extra behavior (slug/technology handling; the
category→skill URL nesting) - CLAUDE.md's "keep business logic out of...
route functions" is satisfied either way since the actual logic lives in
`portfolio_content.py`/the entity-specific service modules, not inline in
either the factory or the hand-written routes. Named per-entity service
wrapper modules (e.g. `experience_service.py`) still exist on top of the
generic engine purely for readability/testability - tests and routes import
`experience_service.create_experience(...)`, not the generic engine
directly.

### 23. Two generic Jinja templates instead of one template per entity
Similarly, `app/templates/admin/entity_list.html` and `entity_form.html`
are reused by every Phase 2 entity type (parametrized by a `rows`/`columns`
list, or by iterating `for field in form`) rather than one bespoke template
per entity. WTForms' `field.label`/field-widget rendering already produces
a correctly-associated `<label for="...">`/`<input id="...">` pair per
field with no per-form template code, satisfying CLAUDE.md's accessibility
("labels", "semantic HTML", "accessible forms") requirements generically.
This keeps the admin UI's markup consistent across all ten entities and
means adding an eleventh content type in a future phase needs a new
model/form/service + a few lines registering it with the existing route
factory, not a new template.

## Phase 3 — Template engine

### 24. "Exactly one active template" is enforced in the service layer, not a DB constraint
A `PortfolioTemplate.is_active` boolean per row needs an "at most/exactly
one true" invariant. A partial unique index (`CREATE UNIQUE INDEX ...
WHERE is_active`) is supported by both PostgreSQL and SQLite, but Alembic's
autogenerate support for partial/conditional unique constraints differs
enough between the two dialects (`postgresql_where=`/`sqlite_where=` are
separate, dialect-specific kwargs on the same `Index`, not a single
portable expression) that it would add real migration complexity for a
guarantee this app never needs to defend against a concurrent writer -
there is exactly one process path that ever sets `is_active`
(`template_service.set_active_template`), and it flips every row's value in
one function call ending in one `db.session.commit()`, so no reader can
ever observe zero or two active rows in this application's own code paths.
Matches this codebase's existing precedent (`OrderingMixin`'s
`display_order` is dense-by-convention, not DB-enforced either - see
`app/models/base.py`'s docstring) of favoring an application-enforced
invariant over a cross-dialect-fragile DB constraint when nothing external
writes to the table. Documented here, and in
`app/models/portfolio_template.py`'s docstring, as the tradeoff to revisit
if a second write path (e.g. a future direct-DB admin script) is ever added.

### 25. Dark/light mode persistence: `localStorage`, not a cookie
Both are reasonable; `localStorage` was chosen because (a) this phase's
toggle only needs to affect client-side rendering (CSS custom properties
via `data-bs-theme` on `<html>`) - nothing server-side branches on the
viewer's mode, so there is no reason to pay the "send it on every request"
cost of a cookie; (b) it keeps the toggle entirely client-side/progressive-
enhancement (CLAUDE.md rule #18), with zero new server code, no new
`Set-Cookie` handling, and no CSRF-adjacent surface to reason about; (c) a
small inline script at the top of `themes/_layout.html`'s `<head>` reads
`localStorage` (falling back to `prefers-color-scheme`) before first paint,
which avoids a flash-of-wrong-mode exactly as well as a cookie would.
Trade-off, recorded for later phases: `localStorage` is per-origin and
per-browser (won't follow a viewer across devices, and would need a
per-viewer preference row in the DB to do that - not needed for a
single-admin content-management app), and a future SSR-rendered public page
that wants to avoid *any* client-side flash on first load (not just the
brief one this inline script already minimizes) could read a cookie
version of the same value server-side; nothing in this phase's
implementation blocks adding that redundantly alongside `localStorage`
later if it becomes worth it.

### 26. Phase 3's "preview" is an admin-only route, not a public one
This phase's task explicitly allows (but doesn't fully specify) "a
representative preview/demo rendering" ahead of Phase 4's full public site.
Since no public portfolio routes exist yet (`app/public/` is still an empty
package - Phase 4 scope) and CLAUDE.md's authorization rule ("Enforce
authorization server-side") applies to every route regardless of phase,
`GET /admin/templates/<key>/preview` was implemented behind the existing
`admin_required` decorator rather than as a new unauthenticated public
route. This means: (a) no new unauthenticated attack surface was added in
this phase: (b) the preview renders the *signed-in admin's own real*
Profile/Experience content (via `profile_service.get_or_create_profile
(current_user)`), not synthetic placeholder data, which is a stronger proof
of "same content, different presentation" than a hardcoded fixture would
be, and is exactly what `tests/test_admin_template_routes.py` and the
end-to-end curl flow in docs/IMPLEMENTATION_STATE.md exercise; (c) Phase 4
can later add a public, unauthenticated equivalent route (e.g. `GET /`
rendering `render_preview(get_active_template().key, ...)` for anonymous
visitors) with no change to `template_service`/the registry/the theme
templates - only a new route in `app/public/`.

## Phase 4 — Public portfolio

### 27. Navigation configuration: a small global model + a code-level
### endpoint allowlist, not free-text URLs
docs/MASTER_PROMPT.md requires "exact public navigation should be
configurable" and CLAUDE.md lists "navigation" as part of the portfolio
content model, but neither specifies the mechanism. Considered: (a) a
free-text URL field per nav entry - rejected, because an admin (or anyone
who compromised the admin account) could point a "nav" entry at an
arbitrary external URL or, worse, at something that *looks* internal but
isn't, and because it decouples the nav config from what routes actually
exist (a typo'd or since-removed path silently 404s for every visitor);
(b) a fixed, hard-coded nav list in the layout template - rejected, fails
"configurable" outright; (c) **the chosen design**: `NavigationItem`
(`app/models/navigation.py`) stores a Flask *endpoint name* (e.g.
`"public.projects"`), resolved through `url_for` at render time, and only
endpoints in `app/services/nav_service.ALLOWED_NAV_ENDPOINTS` (a code-level
list of the real public routes) are selectable via the admin form's
`SelectField`. This is the exact same "code defines what's selectable,
data defines the active/ordered/labeled subset" split Phase 3 already
established for `PortfolioTemplate`/the theme registry, applied to
navigation instead of themes. Migration impact: one new table
(`navigation_items`), no changes to existing tables. Security impact: an
admin can reorder/relabel/hide any of the ten known public pages, or (by
deleting all rows and re-adding a subset) publish a reduced nav, but can
never make a nav entry resolve to anything other than a real, currently-
routable page - closing off both the open-redirect-ish "arbitrary URL in
admin-authored content" surface and the "nav points at a 404" footgun.
Testing approach: `tests/test_nav_service.py` covers `sync_defaults()`,
`is_allowed_endpoint()`, and the full admin CRUD+reorder+IDOR-404 cycle;
`tests/test_public_routes.py`'s `TestNavigationConfiguration` covers a
hidden item disappearing from the rendered public `<nav>` and reordering
being reflected in rendered link order.

### 28. Navigation defaults reseed whenever the table is empty (no separate
### "already initialized" flag)
Unlike `PortfolioTemplate` (which has `is_active` as a durable "has this
ever been configured" signal even after admin activity), a navigation list
has no other state to distinguish "brand-new install, never configured"
from "admin deliberately deleted every nav item." Considered adding a
separate sentinel (e.g. a `SiteSetting`/config row marking "nav
initialized") to preserve a genuinely-empty admin-chosen nav across
requests - rejected as unnecessary complexity for this phase: an
admin-configurable single-portfolio site with zero nav links is not a
useful configuration to preserve, and `sync_defaults()`'s simpler
"empty means use the defaults" rule mirrors `template_service.
sync_registry()`'s existing "no active template yet -> activate the
deterministic default" behavior, so the codebase has one consistent
philosophy for this class of problem rather than two. If a future phase
needs "genuinely empty on purpose" to be representable, add a `SiteSetting`
flag then - `NavigationItem`/`nav_service` do not need to change shape to
support that.

### 29. One shared Jinja template per public page, not five per-theme
### variants
Phase 3 built five *preview* pages (`app/templates/themes/<key>/
preview.html`), each with a thin theme-specific structural wrapper around
the same shared macros. Phase 4 needed ten real pages. Considered: (a)
extending that pattern to ten pages x five themes (50 template files) -
rejected as disproportionate: CLAUDE.md rule #17 ("do not duplicate
portfolio data for each theme") and docs/UI_DESIGN.md ("do not duplicate
domain content") already establish that content/markup should not be
theme-specific, and Phase 3's own CSS work (each `app/static/css/themes/
<key>.css` file redefining the same variable set + a handful of structural
rules) already proves identical markup can look meaningfully different
per theme without any markup duplication; 50 near-identical files would
mean every future content/markup change (a new section, an accessibility
fix, a new field on a macro) needs five coordinated edits, a maintenance
and drift risk with no corresponding user-facing benefit over one file
per page. (b) **the chosen design**: one template per page
(`app/templates/public/*.html`, ten files total), each extending the
existing shared `themes/_layout.html` skeleton and importing the same
`base/_content_components.html` macros; the active theme's stylesheet
class (`theme-<key>` on `<body>`, unchanged from Phase 3) is the only
thing that differs per theme. `themes/_layout.html` itself gained a
`preview_mode` flag so it can serve both Phase 3's admin-only preview
banner and Phase 4's real public nav/footer chrome from one file, rather
than forking the layout. Migration impact: none (template-only change).
Testing approach: `TestThemingAcrossPublicPages` in
`tests/test_public_routes.py` parametrizes all 5 themes x all 10 pages
(50 cases) asserting each renders 200 with that theme's marker class, plus
a same-content-different-HTML check across two themes on the homepage -
proving no page is broken under any theme without needing per-theme
template files to prove it.

### 30. Resume delivery stays URL-only in Phase 4
CLAUDE.md: "for the initial release, support image URLs and a storage
abstraction," and file uploads are explicitly Phase 7 scope
(docs/IMPLEMENTATION_PLAN.md). `Resume.public_url` (already modeled in
Phase 2, alongside an adapter-agnostic `storage_reference` field for a
future local/S3-backed resume) is rendered as a "View / download resume"
link in a new tab (`target="_blank" rel="noopener noreferrer"`) on `GET
/resume`, gated on `download_enabled`. No new model/migration/service work
was needed - this phase only had to build the public route+template
consuming the field that already existed. When Phase 7 adds local file
uploads, `GET /resume` can switch to serving `storage_reference` through a
storage adapter with no template change (the macro already just needs *a*
URL to link to).

### 31. Contact page ships now; the contact form stays inert until Phase 7
docs/IMPLEMENTATION_PLAN.md scopes "contact form... server-side
validation... CSRF... spam protection" to Phase 7, but also lists `GET
/contact` under this phase's public route surface (docs/API_SPEC.md) and
CLAUDE.md's public layout expects a "contact" section. Splitting the
difference: `GET /contact` exists now and shows `Profile.public_email` (a
`mailto:` link, only rendered when the admin has set one - CLAUDE.md's "no
exposure of private admin email in public HTML unless intentionally
configured") plus a contact form that is visually complete and fully
labeled but functionally inert (every input `disabled`, no `action`/
`method`/CSRF token, a note pointing visitors at the mailto fallback
today). This intentionally does not implement any contact *backend* logic
(no route handles a POST, no validation, no rate limiting, no email
adapter) - staying inside this phase's explicit boundary ("form submission
wiring is Phase 7") - while giving Phase 7 a finished page to wire up
rather than a page to build from scratch, and giving today's visitors a
working way to actually get in touch (the mailto link) rather than a dead
end.

## Phase 5 — Blog CMS

### 32. Markdown + sanitizer library choice: `markdown` + `bleach`
CLAUDE.md requires Markdown authoring with syntax highlighting, and
separately, non-negotiably, "sanitize rendered blog HTML"/"do not render
raw unsanitized HTML from blog content." Two credible pairings exist:
`markdown-it-py` + `nh3` (both Rust-backed/fast, a newer choice) vs.
`markdown` (the long-standing, most widely deployed Python Markdown
implementation) + `bleach` (an allowlist HTML sanitizer built specifically
for "take this untrusted-ish HTML and make it safe to render," rather than
a general HTML manipulation library repurposed for sanitization). Chosen:
`markdown` + `bleach`, because (a) `markdown`'s `codehilite`/`fenced_code`
extensions give first-class Pygments-backed syntax highlighting
(CLAUDE.md's explicit "syntax-highlighted code" requirement) with a config
surface (`extension_configs`) directly matching what this app needs, no
custom renderer plugin required; (b) `bleach.clean()`'s allowlist API
(`tags`/`attributes`/`protocols`, `strip=True`) maps directly onto
"explicit allowlist, strip everything else, block non-http(s)/mailto URL
schemes" - exactly the guarantee this app's threat model (XSS via blog
content) needs, via one well-known function call rather than assembling
multiple `nh3`/`markdown-it-py` plugins to reach the same guarantee; (c)
both libraries are mature, widely used in production Python web apps, and
need no Rust toolchain in the Docker build. Trade-off (documented, not
blocking): `nh3` is generally faster; not a concern at this app's scale
(self-hosted single-admin blog, sanitizing on save - see #33 - not on
every request).

### 33. Sanitize-on-save, not sanitize-on-render
Both are defensible: sanitize Markdown -> HTML once at create/update time
and store the result (`BlogPost.rendered_body`), or store only
`markdown_body` and re-render+sanitize on every request. Chosen:
sanitize-on-save, because (a) docs/DATABASE_DESIGN.md's `BlogPost` schema
already includes `rendered_body` explicitly annotated "optional/cacheable"
- the schema itself signals this is the intended shape; (b) it means every
public page request (and the admin full-page preview route) renders a
plain, already-sanitized HTML string with zero per-request Markdown-
parsing/sanitization cost, appropriate for a read-heavy public blog; (c)
"sanitize once, at the one place content enters the system" is a smaller,
more auditable surface than "trust that every render call site remembers
to sanitize" - there is exactly one function, `app/services/
blog_service.py`'s `_apply_fields()`, that ever writes to `rendered_body`,
and exactly one function, `app/services/markdown_service.render_markdown()`,
that is allowed to turn Markdown into HTML at all. Trade-off: if the
sanitization allowlist is ever tightened, already-stored `rendered_body`
values would need a one-time re-render migration/management command to
pick up the new rules - not built in this phase (no such need has arisen
yet), but worth remembering if that allowlist changes later. The admin
preview pane/full-page preview route call the same `render_markdown()`
function against not-yet-saved form input, so a draft's preview always
matches what saving would actually store.

### 34. Scheduling abstraction: computed at query time, not a real background job
docs/IMPLEMENTATION_PLAN.md explicitly asks for a "scheduling abstraction"
(not necessarily a real background job) and CLAUDE.md/docs/ARCHITECTURE.md
lean toward avoiding unnecessary infrastructure (no Redis/Celery in V1
unless required - the same reasoning Phase 1's rate-limiter decision, #14,
already applied). A real scheduler (Celery beat, APScheduler, a cron
hitting an internal endpoint) was considered and rejected: it would add a
new moving part (a scheduler process, its own failure mode of "the
scheduler didn't run") for a guarantee this app can get for free by
computing visibility from a stored timestamp at read time. Chosen design:
`BlogPost.status` ("draft"/"published"/"scheduled") plus
`published_at`/`scheduled_at` columns; `BlogPost.is_publicly_visible(now)`
and the SQL-level equivalent in `app/services/blog_service.py`'s public
query functions treat a post as public once its *effective* timestamp
(`published_at`, falling back to `scheduled_at`) is `<= now` - regardless
of whether that moment was reached by simply waiting (an admin scheduled a
post for tomorrow, and tomorrow arrived) or by an admin directly entering a
past timestamp (this phase's exit criteria explicitly exercises the latter
to prove the mechanism). Migration impact: two nullable, indexed
`DateTime(timezone=True)` columns, no separate "scheduled jobs" table.
Security/correctness impact: no race condition between "the scheduler ran"
and "a visitor requested the page" can exist, because there is no separate
process - visibility is a pure function of already-committed data,
evaluated inside the same request/query that serves the visitor. Testing
approach: `tests/test_blog_models.py`'s `TestVisibility` and
`tests/test_blog_services.py`'s `TestPublishUnpublishSchedule`/
`TestPublicQueries` cover every combination directly; the end-to-end curl
flow in docs/IMPLEMENTATION_STATE.md schedules one post in the far future
and one in the past and confirms via live HTTP requests that only the
past one is public, with no process running in between to "flip" it.

### 35. Slug strategy: reuse the exact `project_service` pattern
`BlogPost.slug`/`BlogCategory.slug`/`BlogTag.slug` each get their own
`slugify()`+`unique_slug()` pair (in `blog_service.py`/
`blog_category_service.py`/`blog_tag_service.py` respectively), copied from
`app/services/project_service.py`'s Phase 2 pattern (lowercase, non-
alphanumeric runs collapsed to a single hyphen, trimmed, `-2`/`-3`/...
appended until unique) rather than inventing a new slugging convention or
introducing a shared `slug_service.py`. Considered a shared helper module -
rejected for this phase as premature abstraction: three call sites with
three different uniqueness scopes (posts globally, categories globally,
tags globally) don't yet justify extracting a generic version, and keeping
each service self-contained matches this codebase's existing precedent of
per-entity service modules over one shared "do everything" service (see
docs/DECISIONS.md #22's discussion of the same tension for CRUD, resolved
differently there because the *engine* is shared - here, only the
*algorithm* is, and copying ~15 lines three times is simpler than adding an
import for something this small). An admin can also supply an explicit slug
(optional form field); leaving it blank falls back to slugifying the title/
name, matching `ProjectForm.slug`'s existing UX.

### 36. Preview mechanism: reuse the sanitize-on-save renderer against
### unsaved form input, not a separate "draft preview" render path
The admin blog form needs to show what a post's Markdown will look like as
HTML before/without saving. Considered a separate, more permissive preview
renderer (e.g. skip sanitization for "it's just an admin previewing their
own content") - explicitly rejected: CLAUDE.md's "sanitize rendered blog
HTML" rule does not carve out an exception for admin-only views, and an
unsanitized preview pane would be a stored/reflected-XSS-adjacent risk if
the admin account were ever compromised, plus it would let a preview lie
about what will actually be publicly rendered. Chosen: `blog_service.
preview_html()` calls the exact same `markdown_service.render_markdown()`
function used at save time, against the form's current (possibly invalid,
possibly not-yet-saved) `markdown_body` value - both the inline preview
pane on the create/edit form (re-rendered on every submit, even one that
fails validation on other fields) and the full-page `/admin/blog/<id>/
preview` route (which previews the last *saved* `rendered_body`, for
reviewing a draft that's already been created) use it. This guarantees
"what you preview is what you get" with zero additional sanitization
surface to maintain.

## Phase 6 — Blog discovery/SEO

### 37. Pagination: in-memory `Page`/`paginate()`, not SQL `LIMIT/OFFSET`
Problem: the blog list/category/tag/search pages all need `page`/`per_page`
pagination with prev/next links and out-of-range handling. Constraints:
CLAUDE.md's "pagination for blog/admin lists" and "no N+1 queries on major
pages" pull in slightly different directions, and `BlogPost` visibility
(`is_publicly_visible`) is a computed property combining `status` and a
coalesce of two nullable timestamp columns - not a single clean SQL
predicate `WHERE` clause could express without duplicating that logic in
raw SQL. Alternatives considered: (a) push pagination into SQL
(`_visible_query(...).order_by(...).limit(per_page).offset(...)`) -
possible (the existing `_visible_query`'s `db.or_` predicate already
mirrors the visibility rule in SQL), but would require either duplicating
the "effective publish date" `COALESCE` ordering logic at every one of the
four call sites (home/category/tag/search) or introducing a shared query-
builder abstraction, for a benefit (avoiding one full-table Python fetch)
this app's scale doesn't need - CLAUDE.md's own "avoid premature
optimization"/"no external API dependency for core functionality" spirit
applies here too. (b) **the chosen design**: a small, dependency-free
`app/common/pagination.py` (`Page` dataclass + `paginate()`) that slices an
already-fetched, already-visibility-filtered Python list - every call site
(`blog_service.list_public_posts_page`/`*_by_category_page`/`*_by_tag_page`/
`search_public_posts_page`) is a one-line wrapper around the existing
unpaginated function, so Phase 5's existing tests and call sites
(`related_posts`, the sitemap, the RSS feed) are completely unaffected.
Migration impact: none. Security impact: `per_page` is clamped to `[1, 50]`
in `app/public/routes.py` before it ever reaches `paginate()`, so a crafted
query string can't force an unbounded slice. Testing approach:
`tests/test_pagination.py` unit-tests `Page`/`paginate()` directly (first
page, partial last page, out-of-range, empty-result-set edge cases);
`tests/test_seo_routes.py` and `tests/test_blog_discovery_services.py`
cover it end-to-end through the routes/services. Trade-off, documented for
later: if post volume ever grows large enough that fetching the full
visible-post list on every request becomes measurably slow, the fix is
confined to `list_public_posts`'s SQL query and `paginate()`'s call
sites - `Page`'s shape (items/page/per_page/total) would not need to
change.

### 38. Out-of-range pagination: 404, not silent clamping
A `page` value beyond the last page of a non-empty result set could
either 404 or silently clamp to the last valid page (or render an empty
list at `page`). Chosen: 404 (`Page.is_out_of_range` - `page > pages`,
computed independent of `total` so an empty result set's own page 2+ is
also correctly flagged, while its page 1 is not). Rationale: a listing page
claiming "here are 0-of-N results" for a page number that was never valid
is a worse UX/SEO signal than a clear 404 (a stale bookmarked/crawled
`?page=7` URL for a blog that's shrunk to 3 pages should read as "this page
doesn't exist," not silently render as if it always had zero posts on page
7); it also matches this codebase's existing precedent of 404 over a
degraded-but-200 response for "this specific identifier doesn't resolve"
(`project_service.get_public_project_by_slug`, `blog_service.
get_public_post_by_slug`). Page 1 of a genuinely empty result set (no posts
at all, or no search matches) is explicitly *not* out of range - it is the
correct empty-state 200, not an error condition.

### 39. Search: SQLAlchemy `ilike()` substring match, not a search engine
CLAUDE.md/docs/MASTER_PROMPT.md ask for blog search but also, repeatedly,
"no external API dependency for core functionality" and (implicitly, via
the whole "avoid unnecessary infrastructure" thread already established for
rate limiting (#14) and scheduling (#34)) no new moving parts unless the
scale demands them. Alternatives considered: (a) Postgres full-text search
(`tsvector`/`tsquery`) - rejected because it's PostgreSQL-specific and this
app's test suite and local dev deliberately also run against SQLite (see
`tests/conftest.py`'s docstring and docs/DECISIONS.md's dialect-portability
precedents, e.g. #24), so a Postgres-only search path would need a parallel
SQLite implementation or would silently degrade in dev/test; (b)
Elasticsearch/a hosted search API - firmly rejected as exactly the kind of
external dependency/infrastructure this app's scale (a single-admin,
self-hosted blog) doesn't justify. (c) **the chosen design**:
`BlogPost.title`/`excerpt`/`markdown_body` matched via SQLAlchemy's
`Column.ilike()`, which SQLAlchemy compiles portably (native `ILIKE` on
PostgreSQL, a `lower(...) LIKE lower(...)` equivalent elsewhere) so the
exact same `blog_service.search_public_posts` code path works unchanged
against both PostgreSQL (production) and SQLite (dev/test). Migration
impact: none (no new index added - acceptable at this app's scale; an
index on `title`/`excerpt` would help a production installation with a
large post volume, worth revisiting then). Security impact: search terms
are passed as SQLAlchemy bind parameters (never string-interpolated into
raw SQL), so there is no SQL-injection surface; only publicly-visible posts
are ever searched (search reuses `_visible_query`), so a draft can never be
discovered by guessing its content. Testing approach:
`tests/test_blog_discovery_services.py::TestSearch` covers title/excerpt/
body matches, case-insensitivity, blank-query handling, and exclusion of
drafts/future-scheduled posts; `tests/test_seo_routes.py::
TestBlogSearchRoute` covers the same through the live route.

### 40. Related posts: shared-tag/category heuristic, ranked by overlap
Problem: docs/MASTER_PROMPT.md/CLAUDE.md ask for "related posts" without
specifying the algorithm. Alternatives considered: (a) a content-similarity
model (TF-IDF/embeddings) - rejected outright as disproportionate
infrastructure for a single-admin blog, and squarely the kind of thing
CLAUDE.md's "avoid premature...dependency" rules exist to head off; (b)
purely "most recent other posts" (no relatedness signal at all) - rejected
because it isn't actually *related*, just "other things to read," which
undersells what a reader would expect from a "Related posts" heading. (c)
**the chosen design**, `blog_service.related_posts(post, limit=3)`: a
candidate must share at least one tag or the same category with `post`;
survivors are ranked by `(tag-overlap-count, same-category, most-recent-
effective-publish-date)`, all descending, so a post sharing three tags
outranks one sharing one tag or only a category, and ties fall back to
recency. Only ever draws from `list_public_posts` (the same visibility-
filtered source every other public query uses), so a draft/future-scheduled
post can never appear as a "related" post regardless of tag/category
overlap. Migration impact: none. Testing approach:
`tests/test_blog_discovery_services.py::TestRelatedPosts` covers
self-exclusion, tag-overlap relevance, category-only fallback,
draft/future-scheduled exclusion, the empty-result case, and the `limit`
parameter; `tests/test_seo_routes.py::TestRelatedPostsOnDetailPage` proves
it renders correctly on a live page.

### 41. Reading time: 225 words per minute, computed from stripped rendered HTML
The commonly cited range for adult silent-reading speed of English prose is
roughly 200-250 words per minute; 225 (the range's midpoint) was chosen as
a reasonable, unremarkable default with no further tuning attempted (this
is an estimate for a UX nicety, not a metric anything else in the
application depends on). Word count is taken from `rendered_body` with
HTML tags stripped via a simple `re.sub(r"<[^>]+>", " ", text)` (falling
back to `markdown_body` if `rendered_body` is somehow unset) rather than
from raw `markdown_body` directly - counting the rendered text avoids
Markdown syntax characters (`#`, `` ` ``, `[...]`/`(...)` link syntax)
inflating the count relative to what a reader actually reads. `minimum 1
minute` avoids ever displaying "0 min read" for a very short post. Migration
impact: none. Testing approach: `tests/test_blog_discovery_services.py::
TestReadingTime` covers the rounding-up behavior, a multi-minute post, the
empty-body floor, and that HTML markup itself isn't counted as words.

### 42. RSS/sitemap paths and format: `/rss.xml` + `/sitemap.xml`, hand-built XML via the standard library
Paths are dictated by docs/API_SPEC.md (`GET /rss.xml`, `GET /sitemap.xml`,
`GET /robots.txt`) - not a judgment call. The *format* choice was: use a
dedicated feed-generation library (e.g. `feedgen`) vs. hand-build the XML.
Chosen: hand-build, using only `xml.sax.saxutils.escape` (standard library)
for text escaping - both RSS 2.0 and the sitemap protocol are simple,
well-specified, small XML shapes (a handful of elements, no namespaces
beyond the sitemap's single `xmlns`), and hand-building keeps this phase
dependency-free per docs/MASTER_PROMPT.md's "no external API dependency for
core functionality" (the same reasoning already applied to search, #39,
and originally to Markdown/sanitization library choices, #32). Every
absolute URL in both documents is built from the already-existing
`BASE_URL` config value, never from the incoming request's `Host` header -
an attacker-controlled `Host` header being reflected into a
machine-consumed feed/sitemap is exactly the kind of "unsafe redirect"/
SSRF-adjacent surface CLAUDE.md's threat model calls out, and `BASE_URL` is
already an operator-configured, trusted value used elsewhere (e.g.
canonical URLs). The RSS feed caps at the 20 most recent publicly-visible
posts (an unbounded feed is its own minor resource-exhaustion/served-
payload-size concern, and 20 is a generous, typical feed size). Both are
kept in a new `app/seo/` route module (already an empty scaffolded domain
package since Phase 0) rather than folded into `app/public/routes.py`, per
the architecture skill's "isolate domains" rule - a distinct concern
(machine consumption of the site) from the human-facing public pages, even
though both read through the exact same visibility-filtered services.
Testing approach: `tests/test_seo_routes.py::TestSitemap`/`TestRssFeed`
parse both documents with `xml.etree.ElementTree` (proving well-formedness,
not just "the response didn't error") and assert on specific expected/
excluded URLs and fields; verified end-to-end against a real Gunicorn +
PostgreSQL server (see docs/IMPLEMENTATION_STATE.md's Phase 6 section).

### 43. OpenGraph image fallback: post's cover image, then the profile's image, then omit
CLAUDE.md/docs/MASTER_PROMPT.md ask for OpenGraph/Twitter Card metadata
without specifying what `og:image` should be when a post has no
`cover_image_url` set (an admin can publish a post with no cover image -
Phase 5's `BlogPost.cover_image_url` is nullable/optional). Alternatives
considered: (a) omit `og:image` whenever the post has no cover image -
simple, but a link shared to a post without a cover image would get a
worse, imageless social-media preview even when the site has a perfectly
good profile photo it could use instead; (b) fabricate/hardcode a generic
placeholder image URL - rejected, since that would either 404 (no such
asset exists) or require shipping a new static asset with no admin control
over it, for a phase whose scope is metadata plumbing, not new content
management surface. (c) **the chosen design**: fall back to
`Profile.profile_image_url` (already-existing Phase 2 content, admin-set)
when the post has no cover image; if neither is set, omit `og:image`/
`twitter:image` entirely and use `twitter:card=summary` instead of
`summary_large_image` (an image-less summary card is the correct Twitter
Card variant, not a broken large-image card pointing at nothing). No new
model/migration work needed - `Profile.profile_image_url` already existed
for Phase 4's hero rendering. Testing approach:
`tests/test_seo_routes.py::TestOpenGraphAndTwitterTags` covers both the
cover-image-present case and the no-image-anywhere case (asserting
`og:image` is entirely absent and `twitter:card` is `summary`, not
`summary_large_image`); verified live against a real published post via
curl (see docs/IMPLEMENTATION_STATE.md).

## Phase 7 — Contact and media

### 44. Spam protection: honeypot + rate limiting only, no CAPTCHA
The Phase 7 task explicitly says "do not add a CAPTCHA dependency" while
CLAUDE.md/docs/SECURITY.md ask for "spam protection/rate limiting" on the
contact form. Alternatives considered: (a) a third-party spam-scoring
API (Akismet-style) - rejected outright, both because it's exactly a
CAPTCHA-adjacent external dependency the task rules out and because it
would violate docs/MASTER_PROMPT.md's "no external API dependency for
core functionality" pattern already applied to search (#39) and Markdown
sanitization (#32); (b) a time-based heuristic (reject a submission faster
than a human could plausibly type it) - considered but not added on its
own, since it's easy for even a simple bot to defeat (sleep before
submitting) and would add a second, more fragile mechanism for marginal
extra coverage; (c) **the chosen design**: a classic honeypot field
(`ContactForm.website`, app/public/forms.py) - invisible to a sighted user
(CSS-clipped off-screen, not `display:none`, since some bots specifically
skip `display:none` fields but still fill in ones that are merely visually
hidden) and excluded from the tab order (`tabindex="-1"`) and from a screen
reader's view (`aria-hidden` on the wrapper) - plus `CONTACT_RATE_LIMIT`
reusing the exact Flask-Limiter pattern `LOGIN_RATE_LIMIT` established in
Phase 1 (#14). A filled honeypot silently drops the submission (no DB
write, no email) while still rendering the same "thanks" response a
genuine visitor gets - not revealing to a bot which field tipped it off,
which would otherwise teach it to leave that field alone next time.
Migration impact: none (no schema for this). Security impact: this is
explicitly a "raise the bar," not a "solve spam" mechanism - a targeted,
form-aware bot that fills every field it finds (including honeypots) is
not caught by this alone; the rate limit is the backstop for that case, and
the message is still persisted either way, so nothing entered by a real
visitor is ever silently lost. Testing approach:
`tests/test_contact.py::test_honeypot_filled_silently_drops_submission`
and the rate-limit-trip test in `tests/test_contact_rate_limit.py`; the
end-to-end curl flow (docs/IMPLEMENTATION_STATE.md) submitted a
honeypot-filled request live and confirmed via the admin message list that
nothing was created for it.

### 45. Email adapter: `ConsoleEmailAdapter` default + `SMTPEmailAdapter`, selected via `MAIL_PROVIDER`
CLAUDE.md requires a "configurable email adapter" with "graceful behavior
when email is not configured." Alternatives considered: (a) a third-party
transactional-email API (SendGrid/Mailgun/SES) - rejected as an
unnecessary external dependency for a self-hostable app with no
requirement for one, and inconsistent with this app's repeated "no
external API dependency for core functionality" thread (#32, #39, #42);
(b) Flask-Mail - considered, but it's a thin wrapper around the same
`smtplib` this app can call directly with less indirection, and adding it
would mean two config surfaces (Flask-Mail's own config keys vs. the
`MAIL_*` keys `app/config.py` already anticipated since Phase 0) for the
same job. (c) **the chosen design**: `app/common/email.py`'s `EmailAdapter`
ABC with two implementations - `ConsoleEmailAdapter` (default,
`MAIL_PROVIDER=console`; logs via the app's structured logger instead of
sending, so a fresh self-hosted install with no SMTP configured has a
fully working contact form on day one) and `SMTPEmailAdapter`
(`MAIL_PROVIDER=smtp`; plain `smtplib`, all connection details from
already-anticipated `MAIL_SMTP_*`/`MAIL_DEFAULT_SENDER` env vars, never
hard-coded). `get_email_adapter()` is the sole factory/selection point -
matching this codebase's existing "external integrations behind adapters"
convention (CLAUDE.md rule #19, already applied to argon2/Markdown-
sanitization). Graceful degradation is layered at two points: `get_email_
adapter()` itself falls back to the console adapter (with a warning log)
if `MAIL_PROVIDER=smtp` but `MAIL_SMTP_HOST` is unset, and
`contact_service.notify_new_message()` catches any exception the adapter
raises and logs it rather than letting a broken mail setup 500 the contact
request - the message has already been persisted by the time notification
is attempted, so a mail failure never loses the visitor's message.
Migration impact: none. Security impact: SMTP credentials are read once
from config at adapter construction time and never logged, echoed in a
response, or embedded in any template - verified live in the Phase 7
end-to-end curl flow (a deliberately-set fake `MAIL_SMTP_PASSWORD` never
appeared in any response body). Testing approach:
`tests/test_email_adapter.py` covers the console adapter's no-op-but-
successful send, the provider-selection/fallback logic, and (via a mocked
`smtplib.SMTP`, no real network) that the SMTP adapter constructs the
correct From/To/Subject/Reply-To/body and calls `starttls()`/`login()`
only when configured to.

### 46. Storage adapter: `LocalStorageAdapter` now, `StorageAdapter` interface designed for S3 later
CLAUDE.md's Media section: "design a storage adapter so S3-compatible/
object storage can be added later," while only requiring image URLs +
"a storage abstraction" for "the initial release." Chosen design:
`app/common/storage.py`'s `StorageAdapter` ABC (`save`/`open_bytes`/
`delete`/`path_for`) with exactly one implementation this phase,
`LocalStorageAdapter`, writing under `STORAGE_LOCAL_DIRECTORY` (default
`instance/uploads` - inside the app's data directory, never a path an
admin/attacker can influence, and outside anywhere Gunicorn/a reverse
proxy would ever execute code from). `get_storage_adapter()` is the only
factory call site; an S3-compatible backend later needs only a new class
implementing the same four methods plus a new branch there - no caller
(app/services/media_service.py, app/admin/routes.py, app/public/routes.py)
would need to change. The interface deliberately does not expose a
`url_for()` method returning an adapter-computed URL - the local adapter's
"URL" is always `url_for("public.media_file", stored_name=...)`, a Flask
route the admin routes/service already know how to build, and a future S3
adapter's URL would instead be a signed/public bucket URL built at the
call site from that adapter's own bucket config - forcing every adapter to
agree on one URL-shape method today would either leak local-specific
assumptions into the interface or under-specify what an S3 adapter needs,
so URL construction is left to callers instead. Every reference into the
adapter (`path_for`/`open_bytes`/`delete`) re-validates the reference
against a strict `^[0-9a-f]{32}\.[a-z0-9]{1,10}$` regex plus a resolved-
path-containment check before touching the filesystem - the "no path
traversal"/"no arbitrary path input" requirement - rather than trusting
that every caller remembers to validate first. Migration impact: one new
table (`media_assets`, an audit trail independent of the storage
mechanism, not the storage itself). Security impact: saved files are
chmod'd `0o640` (no execute bit for anyone) and named with a randomized
UUID4 hex, never derived from the client-supplied filename - even a
`../../../../etc/passwd.png`-shaped upload filename only ever affects the
`MediaAsset.original_filename` display value, never the actual storage
path (verified directly in `tests/test_media_service.py` and live via
curl in the Phase 7 end-to-end flow). Testing approach:
`tests/test_storage_adapter.py` (safe-name generation, traversal
rejection, non-executable file permissions, delete idempotency),
`tests/test_media_service.py` (content-sniffing-driven validation),
`tests/test_admin_media_routes.py` (the full authenticated upload/serve/
delete cycle plus rejected-upload cases through real HTTP requests).

### 47. Media upload integration point: a general-purpose `/admin/media` page, not wired into any single `*_url` field
The Phase 7 task explicitly allows either integration shape: "use this for
at least one existing `*_url`-style field... OR add it as a general-purpose
upload endpoint used by the admin blog/project forms - pick the
integration point that's least invasive given the existing Phase 2/5
forms." Every candidate field (`Project.image_url`, `BlogPost.
cover_image_url`, `Profile.profile_image_url`, `Resume.public_url`) is
currently a plain `StringField` with a `URL()` validator on an already-
shipped, already-tested form (`app/admin/forms.py`). Alternatives
considered: (a) replace one of those fields with a file input + inline
upload-on-submit - rejected as the more invasive option: it would need
per-form JS (an upload-then-fill-the-URL-field flow, since a normal HTML
file input's value can't populate a sibling text field without

used, including cases with no new image), for only one of several
plausible `*_url` fields; (b) **the chosen design**: `/admin/media`
(`app/admin/routes.py`'s `media_list_view`) is a standalone page - upload
an image, get back its public `/media/<stored_name>` URL in a
copy-to-clipboard-style readonly input, paste that URL into whichever
`*_url` field on whichever existing form. Zero changes to `ProjectForm`/
`BlogPostForm`/`ProfileForm`/`ResumeForm` or their templates were needed;
every one of those forms already accepts exactly this shape of value (a
URL string) with no code change. This is explicitly a "ship the
capability now, wire in a nicer per-form upload widget later if wanted"
tradeoff - documented in docs/IMPLEMENTATION_STATE.md's "Known
limitations" - and nothing about `MediaAsset`/`StorageAdapter`/
`media_service` would need to change to add that nicer widget later, only
new form/template/JS work. Migration impact: `media_assets` table only (no
changes to any existing content table). Testing approach:
`tests/test_admin_media_routes.py` covers the upload/list/serve/delete
cycle and authorization directly; no test asserts anything about
`Project`/`BlogPost` forms changing, because nothing about them changed.

### 48. Contact message admin routes: no ownership scoping, same as other single-admin global lists
`ContactMessage` has no `profile_id`/owner column (per
docs/DATABASE_DESIGN.md's schema, which lists no such column) - matching
the existing precedent `BlogCategory`/`BlogTag`/`SkillCategory` already
established (#18) for entities that are global to this single-portfolio,
single-admin application rather than scoped to a `Profile`. The admin
routes (`/admin/messages*`) still use the same "fetch by id, `None` → 404"

### 49. Security headers: a custom `after_request` hook, not Flask-Talisman
CLAUDE.md's Security/Observability sections and docs/SECURITY.md's "Headers"
section ask for CSP, X-Content-Type-Options, Referrer-Policy,
Permissions-Policy, frame-ancestors, and HSTS "in HTTPS deployment," with
an explicit warning: "Do not configure CSP in a way that breaks the
application without testing it." Alternatives considered: (a)
Flask-Talisman - the obvious off-the-shelf choice, but it bundles its own
opinions about force-HTTPS redirects, session-cookie mutation, and a
nonce-generation API that would partially duplicate what app/config.py
already owns (SESSION_COOKIE_SECURE, ProductionConfig.init_app), adding a
second source of truth for cookie/HTTPS policy and one more third-party
dependency for roughly 20 lines of header-setting logic; (b) **the chosen
design**: `app/common/security_headers.py`'s `init_security_headers(app)`
registers one `after_request` hook, in the same "small, dependency-free,
hand-rolled" style this codebase already uses for its other
cross-cutting concerns (`app/common/logging.py`, `app/common/health.py`).
Policy (see that module for the exact string):
`default-src 'self'; script-src 'self'; style-src 'self'
https://cdn.jsdelivr.net; font-src 'self' https://cdn.jsdelivr.net;
img-src 'self' data: https:; connect-src 'self'; object-src 'none';
base-uri 'self'; form-action 'self'; frame-ancestors 'none'` plus
`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
`Referrer-Policy: strict-origin-when-cross-origin`, and a conservative
`Permissions-Policy` denylist (camera/microphone/geolocation/payment/usb/
interest-cohort). `img-src` allows any `https:` origin (not just 'self')
because portfolio/blog images (`Project.image_url`, `BlogPost.
cover_image_url`, `Profile.profile_image_url`) are admin-entered URLs to
arbitrary hosts by design (#46/#47), not a fixed set - CSP's `img-src` is a
client-side rendering restriction, unrelated to docs/SECURITY.md's SSRF
rule (which is about the *server* never fetching those URLs, which this
app already never does). `script-src`/`style-src` need no `'unsafe-inline'`
- see #50 and #51 for how the two inline-script/inline-style sources that
existed before Phase 8 were removed instead of exempted. Migration impact:
none. Security impact: this is the CSP itself - it blocks any injected
`<script>`, inline event handler, or cross-origin resource load a stored-
XSS payload might attempt, on top of Jinja autoescaping and the blog's
Markdown sanitization (#XX). Testing approach:
`tests/test_security_headers.py` asserts every header's presence/value via
the Flask test client (including that HSTS is absent by default and only
appears when `ENABLE_HSTS=true` *and* the request is seen as HTTPS), plus
a live curl-driven check against a real Gunicorn + PostgreSQL server (see
docs/IMPLEMENTATION_STATE.md) that also exercised the full CSRF-protected
login and contact-form POST flows with the CSP active, confirming it does
not break either.

### 50. Removed the one inline `<script>` instead of adding a CSP nonce
Phase 3's `app/templates/themes/_layout.html` had one inline `<script>`
that reads `localStorage` and sets `data-bs-theme` before first paint (to
avoid a flash of the wrong color mode). A strict CSP with no
`'unsafe-inline'` cannot allow that as-is. Alternatives considered: (a) a
per-request CSP nonce (generate one in the `after_request`/context
processor, echo it in both the CSP header and the `<script nonce="...">`
attribute) - works, but adds a moving part (nonce generation, template
plumbing, cache-busting implications for any future response caching) for
a script that has no need to be inline in the first place; (b)
`'unsafe-inline'` for `script-src` - rejected outright, it would defeat
the point of shipping a CSP at all for the one threat (stored XSS
executing via an injected `<script>` tag) it exists to stop; (c) **the
chosen design**: moved the script verbatim into
`app/static/js/theme-init.js` and load it the normal way
(`<script src="...">`), keeping it as the first thing in `<head>` (before
the stylesheets) so the before-first-paint timing is unchanged - an
external same-origin script needs no CSP exemption at all under
`script-src 'self'`. Migration impact: none. Testing approach: existing
theme/dark-mode tests (`tests/test_template_engine.py`,
`tests/test_public_routes.py`) still pass unmodified since the script's
behavior didn't change, only its location; `tests/test_security_headers.py`
confirms no page needs `'unsafe-inline'`.

### 51. Removed inline `style="display:inline"`/`onsubmit`/`onclick` from admin templates instead of exempting them
Six admin CMS templates used `style="display:inline"` (so an action form
sits next to its siblings instead of stacking as a block element),
`onsubmit="return confirm('...')"` (a destructive-action confirmation),
and one `onclick="this.select()"` (select-all on the /admin/media
copyable URL field) - all inline attributes a strict CSP's `style-src`/
`script-src` (no `'unsafe-inline'`) disallows. Rather than weaken the
policy for the admin blueprint only (Flask's CSP header here is
app-wide, and a route-specific policy would be one more thing to keep in
sync as admin templates evolve), all three were replaced with unobtrusive
JS/CSS, matching CLAUDE.md rule 18 ("prefer progressive enhancement over
JavaScript-heavy architecture") and this app's existing pattern of tiny,
single-purpose static JS files (`theme-toggle.js`, `nav-toggle.js`):
- `style="display:inline"` -> `class="d-inline"`, defined in the new
  `app/static/css/admin.css` (the admin CMS previously had *no*
  stylesheet at all - `app/templates/base/layout.html` linked nothing -
  so this is also the first admin CSS file, kept intentionally minimal:
  one utility class, not a redesign).
- `onsubmit="return confirm('...')"` -> `data-confirm="..."` read by a
  `submit` listener in the new `app/static/js/admin-ui.js`.
- `onclick="this.select()"` -> `class="select-on-click"`, read by a
  `click` listener in the same file.
Both attributes degrade safely with JS disabled: the confirm-before-submit
form still submits (just without the confirmation prompt - the underlying
route-level authorization/CSRF/ownership checks are the real safety net,
not the browser confirm dialog), and the select-on-click field is still
readable/selectable manually. Migration impact: none. Testing approach: no
behavior changed from a test's perspective (existing
`tests/test_admin_*_routes.py` cover the routes these forms POST to
unchanged); `tests/test_security_headers.py` plus the live end-to-end
curl run (docs/IMPLEMENTATION_STATE.md) exercised `/admin/templates` and
`/admin/media` under the real CSP to confirm the pages still render/
function.

### 52. Reverse proxy trust: `ProxyFix`, off by default, opt-in via `TRUST_PROXY_HEADERS`
docs/DEPLOYMENT.md's recommended topology puts Nginx in front of Gunicorn,
and docs/IMPLEMENTATION_STATE.md flagged (from Phase 1) that
`SESSION_PROTECTION = "strong"` and the login/contact rate limiters all
key off `request.remote_addr`/`request.is_secure`, neither of which
reflects the real client without a `ProxyFix`-equivalent - behind a naive
proxy setup, every request looks like it came from the proxy's own IP
address, and HTTPS started by Nginx doesn't propagate to Flask's own view
of `request.is_secure` at all. Alternatives considered: (a) always apply
`ProxyFix` unconditionally - rejected: if this app is ever run without a
reverse proxy in front (directly exposed, e.g. a quick local demo, or a
misconfiguration), an unconditional `ProxyFix` would let any client spoof
`X-Forwarded-For`/`X-Forwarded-Proto` and forge its own perceived IP/
scheme, undermining both the rate limiter and (more seriously) making
`ENABLE_HSTS`'s `request.is_secure` check and `SESSION_COOKIE_SECURE`
trivially bypassable; (b) **the chosen design**: `werkzeug.middleware.
proxy_fix.ProxyFix`, wired in `app/__init__.py`, applied only when
`TRUST_PROXY_HEADERS=true` (default `false`), trusting `PROXY_COUNT`
(default `1`) hops - i.e. it must be deliberately turned on by whoever
controls the deployment topology, exactly once Nginx (which overwrites,
not appends to, any inbound `X-Forwarded-*` from the client - see
`deploy/nginx/portfolio.conf`) is actually the sole entry point. The
`proxy` docker-compose profile and `deploy/nginx/portfolio.conf` are
designed together with this flag: the compose file's `app` service leaves
`TRUST_PROXY_HEADERS` off by default (safe with no proxy, e.g. `docker
compose up` without `--profile proxy`) and the sample Nginx config sets
all three `X-Forwarded-*` headers Nginx itself controls. Migration impact:
none. Security impact: without this, `ENABLE_HSTS`'s `request.is_secure`
guard (#49) would never see the request as secure behind a TLS-terminating
proxy and would silently never send HSTS in exactly the deployment
topology (Nginx + Gunicorn) that needs it - `ProxyFix` is what makes that
guard meaningful in production rather than a no-op. Testing approach:
`tests/test_security_headers.py::test_proxy_headers_untrusted_by_default`;
live-verified end-to-end against a real Gunicorn + PostgreSQL server with
`TRUST_PROXY_HEADERS=true` and a spoofed `X-Forwarded-Proto: https` header,
confirming HSTS appears only then (see docs/IMPLEMENTATION_STATE.md) - not
tested against an actual running Nginx (no Docker daemon available in this
build, same constraint every phase has documented).

### 53. Gunicorn tuning: `gunicorn.conf.py`, sync workers, `2 x CPU + 1` capped at 4
docs/IMPLEMENTATION_PLAN.md's Phase 8 scope asks to "confirm Gunicorn
configuration is production-appropriate." The Phase 0-7 command line
(`--workers 3 --timeout 30`) was a fixed guess, not derived from anything.
Alternatives considered for worker model: gthread/gevent async workers -
rejected, every request this app serves is a normal blocking DB round
trip (SQLAlchemy/psycopg2-style blocking I/O, not `async def` routes), so
an async worker model buys nothing and adds a dependency (`gevent`) plus a
new monkey-patching failure mode. Chosen: `worker_class = "sync"` (
Gunicorn's default), `workers = min(2 * cpu_count() + 1, 4)` - the
standard Gunicorn sizing formula, capped so a small VPS doesn't
oversubscribe memory (each worker holds its own SQLAlchemy connection
pool) by default; both are overridable via `GUNICORN_WORKERS`/
`GUNICORN_WORKER_CLASS` env vars for a bigger box. `preload_app = False`
(explicit, not just the default) because this app builds its DB engine
inside `create_app()` - preloading would build that engine/connection
pool once in the master process before `fork()`, which every worker
would then share/corrupt (the well-known psycopg-and-fork hazard).
`graceful_timeout = 30` matches `timeout = 30` so an in-flight request
during a rolling restart/SIGHUP gets the same grace Gunicorn already gives
a slow request, not cut short. `max_requests = 1000` (jittered by 100)
recycles workers periodically as cheap defense-in-depth against slow
memory growth, without needing to know whether this app actually leaks
memory (Gunicorn's own recommended practice). Every value is overridable
via `GUNICORN_*` env vars rather than requiring an edit to
`gunicorn.conf.py` itself. Migration impact: none (the Dockerfile's `CMD`
changed from an inline `gunicorn --bind ... --workers 3 ...` to
`gunicorn -c gunicorn.conf.py wsgi:app`; docker-compose.yml's `app.command`
was updated to match). Testing approach: started this exact config with
real Gunicorn against a real PostgreSQL server and confirmed 4 workers
booted and served requests correctly (docs/IMPLEMENTATION_STATE.md) - no
automated test covers process-management config directly (nothing in this
app's test suite runs under Gunicorn; the Flask test client is
process-model-agnostic by design), consistent with how Phase 0's Gunicorn
command line was verified.

### 54. Migration-on-boot stays the default (single instance); a `migrate` profile documents the multi-instance alternative
docs/IMPLEMENTATION_PLAN.md's Phase 8 scope explicitly asks to "review...
and decide/document whether that's still appropriate for production or
should change." This app's target deployment (docs/DEPLOYMENT.md: "VPS,"
"Compose service for small deployments"; docs/DECISIONS.md #14's
`memory://` rate-limit storage, which is itself only correct
single-instance) is a single `app` container, for which `flask db upgrade
&& flask bootstrap-admin && exec gunicorn ...` on every start is safe and
simple: both commands are idempotent (`bootstrap-admin` no-ops if the
admin already exists; `flask db upgrade` no-ops if already at head), and
with exactly one instance there is no other process to race against
during the upgrade. This was kept as the default rather than changed.
However, if this app is ever scaled to more than one `app` replica (e.g.
behind a load balancer), running `flask db upgrade` from every replica's
boot is unsafe - concurrent `ALTER TABLE`s from two replicas starting at
once, or one replica running new code against not-yet-migrated schema
while another is mid-migration. docker-compose.yml now also defines a
profile-gated `migrate` one-shot service (`docker compose run --rm
migrate`, not started by a plain `docker compose up`) running exactly
`flask db upgrade && flask bootstrap-admin` and nothing else, documented
in docs/DEPLOYMENT.md as the step to run once, before scaling `app` past
one replica (and to then drop `flask db upgrade`/`flask bootstrap-admin`
from `app`'s own command, leaving it as `exec gunicorn -c
gunicorn.conf.py wsgi:app` only). Migration impact: none (no schema
change). Security/correctness impact: prevents a concurrent-migration race
in a topology this app doesn't ship as the default but documents a path
to. Testing approach: config/documentation only, consistent with every
other docker-compose-shaped claim in this project (no Docker daemon has
been available in any build session - see docs/IMPLEMENTATION_STATE.md);
`flask db upgrade` and `flask bootstrap-admin` themselves were re-verified
individually against a real PostgreSQL server this phase (see
docs/IMPLEMENTATION_STATE.md).

### 55. Container hardening: read-only root filesystem, dropped capabilities, no-new-privileges
docs/DEPLOYMENT.md's "Container requirements" and docs/IMPLEMENTATION_PLAN.
md's Phase 8 scope ask for capability-dropping "if easy" and a read-only
filesystem "where feasible." The non-root user, minimal `python:3.12-slim`
base, multi-stage build (builder stage's `build-essential`/`libpq-dev`
never reach the runtime image), and healthcheck already existed from
Phase 0 and were re-verified, not changed. New this phase, in
docker-compose.yml's `app`/`migrate` services: `read_only: true` (the
container's root filesystem is mounted read-only; the app writes nothing
outside `/app/instance` - uploads via `STORAGE_LOCAL_DIRECTORY`, Phase 7 -
and `PYTHONDONTWRITEBYTECODE=1` already stops `.pyc` writes), a `tmpfs`
mount at `/tmp` (Werkzeug spools large multipart uploads there before
Phase 7's content-sniffing validation runs), a named `media_uploads`
volume mounted at `/app/instance` (so uploaded media - and the SQLite dev
fallback DB, if ever pointed there - survive container recreation despite
the read-only root), `security_opt: [no-new-privileges:true]` (blocks a
process from gaining privileges beyond what it started with, e.g. via a
setuid binary - defense-in-depth even though nothing in this image is
setuid), and `cap_drop: [ALL]` (Gunicorn binds a non-privileged port
`8000` and does nothing else that needs a Linux capability, so nothing
needed to be added back with `cap_add`). Alternatives considered for the
base image: a `distroless`/`alpine` runtime image - rejected, `psycopg[
binary]` ships a manylinux (glibc) wheel and Alpine's musl libc would
require compiling `psycopg` from source in the runtime stage too
(reintroducing `build-essential`/`libpq-dev` there, defeating the
multi-stage split's whole point); `python:3.12-slim` was already the
minimal glibc-compatible option and was kept. Migration impact: none.
Security impact: a container escape or RCE inside the app process now
cannot persist a backdoor to the image filesystem, install a setuid
binary, or use most Linux capabilities even if it achieves code execution
- it's confined to `/tmp` (tmpfs, wiped on container recreation) and
`/app/instance` (the one directory it's supposed to write to anyway).
Testing approach: config-only - `docker build`/`docker compose up` remain
unverified in this build session (no Docker daemon available, same
constraint as every prior phase - see docs/IMPLEMENTATION_STATE.md); the
Dockerfile and docker-compose.yml were reviewed manually and
docker-compose.yml's YAML (including the new `migrate`/`proxy` services
and the `&app_environment`/`*app_environment` anchor reuse) was confirmed
to parse correctly with PyYAML. `.github/workflows/ci.yml`'s new
`docker-build` job will build the image for real on GitHub Actions'
own Docker-equipped runners on the next push - see #57.

### 56. Nginx reverse proxy: a documented standalone config + a profile-gated compose service, not a required part of `docker compose up`
docs/DEPLOYMENT.md already recommended Nginx in front of Gunicorn but
shipped no example config. Added `deploy/nginx/portfolio.conf` (a

### 57. Dependency audit: `pip-audit`, two dev-only findings accepted as risk, one new CI job
Ran `pip-audit` (added as a dev dependency for this audit, not a runtime
one) against this project's exact pinned/locked environment. Findings:
`black==24.10.0` (the version this project's `pyproject.toml` `dev`
extra's `black>=24.8,<25.0` constraint resolves to) - PYSEC-2026-2120 and

`[project.optional-dependencies].dev`) - the Dockerfile's runtime stage

value or a compromised GitHub Action config; `pytest`'s tmpdir CVE is
about predictable/insecure temp-directory permissions on a shared
multi-user machine, not relevant to isolated CI runners or a single
developer's own machine). Revisit at the next real reason to touch
`pyproject.toml`'s dev pins (or proactively before either upgrade becomes
urgent). `.github/workflows/ci.yml` gained a `dependency-audit` job

preinstalled, unlike this project's own dev/build sandbox (see
docs/IMPLEMENTATION_STATE.md), so this is safe to add even though it
can't be exercised locally. While auditing `.github/workflows/ci.yml`, a
pre-existing YAML bug was also found and fixed: the `test` job's
`env.DATABASE_URL`/`env.TEST_DATABASE_URL` values

scalars ending in a bare `:` with nothing after it on the line, which

these lines predate Phase 8 and CI had run before, but it was never
round-tripped through a standalone YAML parser until this phase's

`tests/test_security_headers.py`), `ruff check .`, `black --check .`,

output; `pip-audit --progress-spinner=off` run directly (not just via the
new CI job, which hasn't executed on GitHub Actions yet in this session);
`.github/workflows/ci.yml` and `docker-compose.yml` both confirmed to
parse as valid YAML via PyYAML.
